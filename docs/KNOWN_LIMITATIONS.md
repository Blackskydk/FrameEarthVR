# Known limitations

- Runtime and editor-test sources compile cleanly with Unity 6000.3.14f1's Roslyn compiler. A full Test Runner pass could not be started while this checkout was already open in another Unity process, and the new headset interactions still require an in-headset pass.
- Grab is right-hand-only and requires an actual physics hit (a first headset pass found the earlier two-handed grab and sky/ellipsoid-fallback grab both undesirable, so both were removed). The previous translation-only, distance-gain behavior has now been replaced by a hard pointer-endpoint constraint, including a before-render solve for OpenXR's late controller pose; this revision needs its first headset pass.
- The Flight↔Grounded scale transition is on its **fourth** revision after three rounds of in-headset feedback, two of which made no visible improvement or made things worse:
  1. A pivot-preserving `SetUserScale` call only keeps a point's *geographic* identity fixed, not the camera's actual world position (altitude is itself scale-relative) — still moved the eyes, could still leave the viewer floating.
  2. `SetUserScaleKeepingObserverFixed` plus an analytic two-sample calibration fixed the eyes-move problem in principle, but a bounded physics raycast alone cannot find the ground from typical Flight altitudes, so the calibration point itself was often wrong or missing.
  3. Replaced the analytic solve with a generic root-finder (secant iteration) searching in raw scale-space, out of caution about the analytic formula — this was very likely a *regression*: the true relationship (a point's mapped height vs. scale) is a hyperbola in scale, not remotely linear, so a general-purpose root-finder using widely-separated sample points converges slowly or to a wrong value against it. This is the most likely explanation for the report being unchanged, and for ending up underground (a badly wrong scale, not just a missed calibration point).
  4. Current: reverted to an *exact* two-sample algebraic solve — but now correctly framed as linear in `1/scale` (which it provably is, algebraically, for this kind of uniform scaling), with the second sample point chosen close to the first rather than at a scale-range extreme, and `BeginTransitionToAltitudeHeight` is a coroutine that falls back to Cesium's unbounded `SampleHeightMostDetailed` height query when the raycast can't find ground at altitude. Diagnostic `Debug.Log`/`Debug.LogWarning` lines were added around the solve (`GroundingController.BeginTransitionToAltitudeHeight`/`SolveScaleForWorldHeight`) specifically so that if this is *still* wrong, the actual computed values (start scale, target floor height, the two calibration samples, the raw vs. clamped solved scale) are available to diagnose from — rather than continuing to guess blind. If it fails again, capture those log lines.
  - Shoulder boost is now an exclusive locomotion modifier in both modes: it applies the same eased travel multiplier in Grounded and Flight and suppresses simultaneous grab/rotate/scale gestures while held.
- Current follow-up: every mode change performs a visually invariant ECEF rebase at the camera, Grounded freezes locomotion during its scale solve, keeps floor correction active even while stationary, and uses WGS84 as a bounded-time fallback when detailed terrain sampling cannot answer. Flight preserves the current user scale so a curved-Earth view is not lost on mode change. Flight motion uses swept-sphere collision against loaded terrain rather than relying on the non-blocking ground-approach speed curve alone. These changes compile but require the next headset pass.
- Drag momentum, boost easing, the world-space comfort vignette, and the asymmetric-smoothed/lookahead ground-approach and grounded-floor-following safety nets (the latter now sharing the same instant-tighten/gradual-relax plus forward-lookahead approach) have each had one round of in-headset feedback and a fix; expect another pass of small tuning fixes in `WorldManipulationController.cs`, `NavigationController.cs`, `GroundingController.cs`, and `ComfortVignetteController.cs`.
- Cesium terrain, imagery, and buildings require a locally supplied Cesium ion token and network connectivity.
- Location search uses the public OpenStreetMap Nominatim endpoint for this personal prototype. It performs only explicit searches, caches results in memory, and enforces a one-request-per-second limit. A distributed or higher-traffic release needs a hosted or commercial geocoder.
- Planetary labels and type-ahead suggestions use a curated offline catalog, not a live POI database. It includes major cities, geographic landmarks, national parks, and selected prominent POIs without adding API calls or usage-based cost, but additions and real-world name changes require updating the catalog in the app. Pressing the explicit Search button remains the fallback for uncatalogued places and does call Nominatim.
- The hand menu uses a lightweight physics ray for its own controls, not the full XR Interaction Toolkit UI sample stack.
- The supported search input is EarthVR's built-in world-space keyboard. `SteamVrSystemKeyboardProvider.cs` is retained as experimental integration source, but `EARTHVR_STEAMVR` is intentionally not defined: enabling it inside `EarthVR.Runtime` creates an invalid dependency on the separately imported, Windows-only SteamVR assembly and breaks the PC compile. Before enabling that provider, move it into a small optional Windows bridge assembly that references both `EarthVR.Runtime` and `SteamVR`; the bootstrap can then discover the bridge without making Android depend on it.
- Re-importing the SteamVR Unity Plugin from scratch needs two follow-up steps, since `Assets/SteamVR/` is gitignored in its entirety and neither survives a fresh import:
  - Delete `Assets/SteamVR/InteractionSystem` (~66 MB of unused bow-and-arrow/buggy/NPC demo content). It depends on the Particle System, Animation, Vehicles, and AI built-in modules, which this project doesn't enable, and it shares `SteamVR.asmdef` with the actual OpenVR bindings the keyboard provider needs, so its compile errors block that whole assembly.
  - Remove the stray `using Valve.VR.InteractionSystem;` from `Assets/SteamVR/Editor/SteamVR_AutoEnableVR_2019plus.cs` (unused even before the folder above is deleted, but only becomes a compile error once that namespace is gone).
  - `autoEnableVR: 0` itself (which suppresses an unwanted "Legacy VR vs. Unity XR" backend-switch prompt on script reload) lives in `Assets/SteamVR_Resources/Resources/SteamVR_Settings.asset` — outside `Assets/SteamVR/`, on purpose per Valve's own convention for local/generated config, so it **is** committed and survives a fresh plugin reimport. Don't confuse it with any `SteamVR_Settings.asset` that might get created directly inside `Assets/SteamVR/Resources/` — that copy is not the one the plugin actually reads (confirmed by testing) and would silently do nothing.
  - Importing the `com.valvesoftware.unity.openvr` package (bundled as a `.tgz` under `Assets/SteamVR/OpenVRUnityXRPackage/`, referenced via a local `file:` path in `Packages/manifest.json`/`packages-lock.json`) previously auto-added a second "OpenVR Loader" to the **Standalone** XR Plug-in Management target alongside OpenXR and disabled Automatic Loading/Running there — causing frozen head tracking and a hang/crash in that build target (Android's settings were untouched and unaffected). Fixed directly in `Assets/XR/XRGeneralSettingsPerBuildTarget.asset` (committed), but if reinstalling the plugin fresh, check **Project Settings → XR Plug-in Management → PC, Mac & Linux Standalone** afterward and confirm only OpenXR is enabled.
  - Note `Packages/manifest.json`/`packages-lock.json` reference that local `.tgz` inside the gitignored `Assets/SteamVR/`; if those two files are ever committed as-is, a fresh clone without `Assets/SteamVR/` present will fail to resolve packages on project open (not just miss the keyboard feature) until either the SteamVR folder is restored or that line is removed again.
- Automatic origin rebasing, complete-viewpoint bookmarks, recent-place history, loading-gated arrivals, the left-hand map globe, seamless planetary travel, and altitude-aware horizon presentation compile against the pinned Unity/Cesium APIs but still need their first in-headset interaction and comfort pass. In particular, verify that a rebase during very fast intercontinental flight is visually imperceptible, the Blue Marble longitude alignment matches selected destinations, the city→globe→great-circle orbit→city path remains comfortable while the head is moving, load-adaptive descent avoids visible tile holes without feeling stalled, the softened horizon hides the last streaming boundary, and the default 85% arrival threshold gives a useful reveal on both PC and Steam Frame networks.
- Loaded tile counts are not exposed by Cesium's public API; the overlay reports view load percentage and memory instead.
- Controller models/haptics, general saved preferences, bookmark renaming, and polished place-management menus are outside the current milestone.
- 90 FPS is a target, not a verified result. Tile density, network, driver, SteamVR render resolution, and location materially affect it.
- Steam Frame performance and controller behavior are unverified without device testing.
